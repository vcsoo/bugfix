# 「정상 처리」 버튼을 누를수록 같은 퇴근 기록이 쌓였다 — 2026-11-05

| | |
|---|---|
| **프로젝트 성격** | 사내 업무 시스템 (출퇴근·급여·발주, 관리자가 사람 실수를 보정하는 화면이 많음) |
| **축** | 3 상태 · 10 동시성 · 12 사람 |
| **등급** | 높음 |

## 무엇을 어떻게 찾았나
실데이터를 읽기만 하는 점검으로 「같은 날 출근 2개 이상」「같은 시각 퇴근 여러 개」 를 셌더니 세 사람의 하루에서 같은 퇴근이 3~5개씩 나왔다.
상태 축으로 「그 날의 판정 × 판정마다 뜨는 보정 버튼」 격자를 그렸더니 원인이 보였다.
- 출근이 퇴근 없이 두 번 들어간 날(QR 출근 + 관리자 수기 출근)을 판정 함수는 「퇴근 누락」 으로 봤다.
- 그래서 「정상 퇴근 처리」 버튼이 떴고, 넣은 퇴근은 **두 번째 출근**과 짝지어졌다.
- 첫 출근은 여전히 퇴근이 없으니 판정은 그대로 「퇴근 누락」 — 버튼이 다시 떴고, 관리자는 누를 때마다 퇴근을 하나씩 더했다.
같은 시기에 직원 쪽에서는 정정 요청이 1~2초 간격으로 7~8개씩 들어와 있었다(보내기 버튼을 눌러도 반응이 늦어 계속 누름).

## 왜 시험이 못 잡았나
시험은 「퇴근 누락인 날에 정상 퇴근 처리를 누르면 퇴근이 들어간다」 처럼 **판정이 맞다는 전제**로 버튼 하나씩만 봤다.
「판정이 원인과 다를 때 버튼을 누르면 상태가 나아지는가」 를 묻는 시험은 없었다 — 판정과 보정을 한 격자에 놓고 보기 전에는 그 질문이 안 나온다.
또 시험은 늘 한 번만 눌렀다. 같은 동작을 연달아 누르는 경우(두 번 클릭·느린 화면)는 사람 축을 돌아야 나온다.

## 어떻게 막았나
- 판정에 「기록 중복」 을 따로 두고(퇴근 없는 출근이 중간에 남음 · 같은 시각 기록 여럿), 그 판정에는 **보정 버튼을 띄우지 않고** 하루 상세에서 사람이 지우게 했다.
- 기록을 넣는 모든 입구(수기 추가·정상 처리·시각 수정·승인)가 같은 「겹침 검사」 를 부르고, 쓰기는 「같은 시각·같은 종류가 없을 때만」 조건으로 한 번 더 막았다.
- 같은 내용의 대기 요청은 새로 만들지 않고, 하나를 처리하면 같은 내용의 나머지도 함께 닫는다. 폼은 한 번 보내면 몇 초간 다시 안 보낸다.
- 재현 시험: 겹친 날에 보정 버튼이 없는지, 겹침을 만드는 수기 입력이 거절되는지, 같은 요청 3번 → 1건, 동시 승인 2번 → 기록 1줄.

## 다른 프로젝트에 옮길 수 있는 교훈
- **자동 보정 버튼은 판정이 틀리면 데이터를 더 망친다.** 「판정 × 보정 동작」 격자를 그리고, 보정 뒤 판정이 실제로 바뀌는지 시험한다. 원인이 애매한 상태에는 보정 버튼을 두지 않는다.
- 실데이터에서 「같은 것이 몇 초 사이에 여러 번」 을 세어 보면, 이중 제출과 보정 고리가 코드보다 먼저 보인다.
